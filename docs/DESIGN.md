# keel — design and build spec

Binding spec for the core build: design v0.6 + ship-gate spec v0.3 + the 2026-10-11 spike results (the spike wins on conflict). Where it is silent, choose the smallest behavior that satisfies it and report the choice as a deviation. MUST / MUST NOT / MAY are normative. All keel files are English. Runtime: Node 24 or newer, built-ins only, running TypeScript directly through type stripping (`erasableSyntaxOnly`, no build step). No Python.

## 1. Purpose and principles

Few principles, each at the strongest feasible layer; every rule enters and leaves through a ledger; verification weight follows risk; public by default, company data private; no re-accretion.

| ID | Charter principle | Strongest layer |
|---|---|---|
| K1 | An author never judges its own output. | hook (ship-gate) |
| K2 | Every done/pass claim carries machine-verifiable evidence. | hook (report-gate) |
| K3 | Changed logic ships with tests in the same diff. | repo CI ▸ hook (ship-gate) |
| K4 | Ask when ambiguous; act when clear. | skill (refining-requests) |
| K5 | Change only what the request needs, minimally, in code a person can follow. | repo lint ▸ skill (writing-readable-code) |

- Charter rows skip the rule of two (they carry `justification`), never expire, and still need a metric (eval), enforced after `grace_until`.
- writing-readable-code R1–R16 are not ledger rows but K5 sub-checks `[K5.1]`–`[K5.16]`, frozen at 16, outside caps.
- Core experiment `risk`: "Verification weight is proportional to risk." Scope `core`, enforced by ship-gate, `review_by` = end of the two-week post-swap pilot (6.1); charter if the pilot holds. The pilot read drop (6.1 Result): `light` is retired, and `risk` keeps the standard, heavy and smoke-only tiers.
- Floor (not principles; no rule of two): `F-irreversible` (irreversible actions need explicit user approval; shipping: at merge, 5.4) · `F-secrets` (no secrets or private-lexicon terms in commits, PR bodies, logs or docs the agent writes) · `F-attribution` (no AI attribution in commits or PRs) · `F-force-push` (no force push to shared branches) · `F-hookskip` (an agent never switches hooks off, 5.6) · `F-mod-trust` (every installed Claude Code mod is reviewed: listed in the overlay's reviewed-mods.txt or committed unmodified in the overlay; smoke `mod-trust`, (e)).

## 2. Enforcement ladder

`repo` (lint, architecture tests, CI in the target repo) > `hook` > `skill` > `prose` = the ledger `layer`. A rule enters at the strongest feasible layer; `skill`/`prose` require `why_not_stronger`. Descending to a repo: `layer=repo`, `enforced_at=repo:<owner/repo>:<path>`, keel's own text deleted; metric = existence check (`git show origin/<base>:<path>`) + CI results; zero violations is success, so repo rows never zero-count demote. Public keel keeps the method (core, skills, `descending-findings`); company repo rules live in the overlay ledger.

## 3. Repos and layout

- `~/git/keel` (public goal): core (principles, ledger engine, smoke, ship-gate, review engine, measurement, descending-findings), `stacks/`, `ledger.tsv` (core and stack rows), example data. `~/git/keel-overlay` (private): company and personal data ((a)). `~/.claude` (private): data only (transcripts, memory, logs, state); harness paths in it are symlinks or generated files, gitignored there.
- Links point at a dedicated checkout that moves only by merge; development happens in `~/git/keel-wt/<topic>`. `bin/link --write` MUST refuse when `KEEL_HOME` is a linked worktree (`git rev-parse --git-dir` ≠ `--git-common-dir`) unless `--allow-worktree`. Linked names keep their v1 paths (`skills/<name>`, `commands/`, `agents/`, `workflows/`, `bin/`, `mcp/`).
- `~/.claude/CLAUDE.md` is generated ((h)); no `@import` anywhere (absolute out-of-project imports are silently skipped). keel owns exactly the `hooks`, `permissions`, `env` keys of `~/.claude/settings.json` ((g)).
- Two ledgers (keel, overlay); smoke checks their union; company rows only in the overlay. Stacks now: `spring-maven`; `mysql-ops`, `react-fe`, `review-lenses` come in migration.

## 4. Ledger

Format: (b).
- **Caps** (retired rows excluded): charter ≤ 7 · core ≤ 10 (floor rows excluded) · per stack ≤ 10 · stacks ≤ 5 · overlay ≤ 15 · hook script files ≤ 8 (distinct script paths in the merged settings `hooks`; 5 today) · generated CLAUDE.md ≤ 4608 bytes (`bin/link`) · each `projects/*/memory/MEMORY.md` ≤ 8192 bytes (per project, apart from CLAUDE.md; WARN) · smoke assertions ≤ 2 × active ledger rows + 40 (one assertion = one check kind × one scope, never per path).
- **Rule of two:** rows neither `scope=charter` nor `type=floor` need ≥ 2 distinct incident refs: `docs/incidents/<name>.md` (must exist in keel) or `private:<id>` (overlay ledger only). Failing rows are GRACE, not FAIL, while `grace_until` ≥ today. When a keel row fails or is in grace, memory files whose frontmatter says `type: feedback` are listed as incident candidates, never FAIL.
- **Metric:** every active row has one (`measure/run`, (e)); zero recognized items = FAIL, GRACE while today ≤ `grace_until`.
- **Expiry (proposals only):** non-charter, non-floor rows carry `review_by` (default creation + 60 days; charter and floor `-`). `measure/propose` (weekly overlay scheduled task) over rows past `review_by`: count 0 → propose demotion (`hook`→`skill`→`prose`→`status=retired`); count > 0 → `review_by` + 60 days; repo rows: failing existence check → re-check, zero violations never demotes. A metric whose runner errored (crash, non-zero exit, no JSON) is never count 0 and never yields a demote/retire proposal; it is a `recheck` with the error as reason. `--model-upgrade <model>`: one re-review proposal per active row (an A/B diff is a separate user-approved step). Output: stdout only. Nothing edits a ledger; the user applies an approved proposal by editing the row. `status=proposed-demote` = accepted for demotion at the next edit; still counted in caps. `type` is classification only, never a demotion axis.
- Every outside rule (plugin distillation, sync jobs) enters only through a ledger row.
- **[ID] tagging:** in every rule location each bullet line (`^\s*(?:[-*+]|\d+\.)\s+`) MUST continue with `[<ID>]`, an active ledger id or `K5.<1-16>`. Rule locations: `PRINCIPLES.md`, overlay `PERSONAL.md`, the rules section of every `SKILL.md` (any `## Rules` heading variant, with qualifier or trailing colon, to the next `## `), every hook deny/warn message (checked by each hook's tests, and at runtime by smoke: every fires `rule_id` exists in a ledger).

## 5. Ship-gate

Gates branch `git push` and `gh pr merge`; both need review and tests evidence, approval only at merge (5.4). Question: is every outgoing path, with the same content and mode, in the diff ONE evidence bundle (review chain + tests + approval) reviewed? Enforces K1, K3, risk. A person pushing from their own terminal is the deliberate escape hatch.

### 5.1 Comparison model
- **C (outgoing):** `git diff --raw -z --no-renames <mb> <head>`, `mb = git merge-base <base> <head>`: `(path, new_blob | deleted, new_mode)`; a rename = delete + add.
- **E (reviewed):** `(path, blob | deleted, mode)` of the diff a review saw: working tree `review_base` → snapshot tree; commit range (`head:<sha>`, promote) `review_base` → `<sha>`, checked-out tree irrelevant; delta `since` tree → reviewed tree.
- **Chain:** one root review (`since` null, `root_run_id = run_id`) plus deltas, each pointing at the previous review evidence of the same repo and root, with a new `run_id` and inherited `root_run_id`. A multi-repo run writes one evidence per repo, same `run_id`. E = fold root → head, later wins per path. Head = review evidence with no successor.
- **Verdict per repo** (one chain covers all of C, else an approved series below; unrelated evidence never combines):
  1. Head verdict `PASS` (earlier links MAY be `NEEDS_FIXES`; a later delta must resolve their findings).
  2. Base scope: the root's `review_base` equals or is an ancestor of `mb` (`git merge-base --is-ancestor`); a narrow base (`HEAD~1`) fails.
  3. Every non-gitlink C entry is in E with the same blob and mode, or its blob is a comment-only deletion (5.4) of the reviewed blob; a deletion needs `(path, deleted)` in E; a missing path fails.
  4. Review kind, tests, smoke, approval per 5.4.
  5. Provenance: every chain review has `source.agent_id`, and its `source.agent_type` is not `fork` (a fork inherits the author's conversation). A reviewer whose transcript shows Edit, Write, NotebookEdit, MultiEdit, or a Bash write outside a temp dir (`/tmp`, `/private/tmp`, `/var/folders`, `$TMPDIR`) is an author: no review evidence, K1 warn with detail starting `reviewer-mutated`.
- **Approved series:** when no one chain covers C, the range from `mb` to head splits into intervals, each judged by rules 1–5 against one chain with an approval bound to its head (push included): consecutive chains (the interval is the chain's `review_base` → a commit whose tree it reviewed), or chains reviewed in parallel and stacked by rebase (the interval is a run of first-parent commits, from the run's first parent to its last commit, and the root's `review_base` equals or is an ancestor of the run's first parent). Every interval must be covered; tests still cover the head's content (5.4). Two stacked chains that changed one path still pass when their hunks are disjoint: an interval's blob counts as reviewed when the chain's reviewed change (`review_base` blob → reviewed blob) merges cleanly (`git merge-file`) onto the blob at the interval's first parent and gives the interval's blob. Hunks that overlap or touch (no unchanged line between) conflict, so the stacked blob is in neither review and the push fails. The deny names that path, its reviewing chains and the last commit that changed it, unless that commit is itself one reviewing chain's change on its parent; a review of that commit from its parent, approved, joins the series as a consecutive interval.
- **Promote:** a `gh pr merge` whose PR base is not the row's integration base (develop → production) is judged per chain without per-chain approval: every interval of the approved series needs only a PASS chain, and the merge needs one `promote` approval whose `head` is the merged sha (`keel approve --promote <owner/repo> <sha>`; none where `auto_merge=true`). `keel evidence promote-plan` lists, per first-parent step from `mb`, the chain root that covers it (fewest uncovered steps) and the contiguous uncovered runs; a deny with uncovered steps names that command. A review of one run (`review_base` = its oldest commit's parent, `head` = its newest commit) joins the series as a consecutive interval, so a promote reviews only commits no develop chain covered.
- Passes: conflict-free rebase, branch rename, one change over several pushes, a comment-only deletion after review (5.4). Fails: any other content, mode or path change after review (incl. rename); reverting to an older non-base value, unless that value is a comment-only deletion of the reviewed blob (5.4).
- Gitlinks (mode 160000) skip blob matching (5.5).

### 5.2 Block points and range

| Command | Action | head / base |
|---|---|---|
| `git push [remote] [src[:dst]…]` (branches) | gate | head = each refspec's `src` (none: HEAD); remote = the first positional word, else `--repo`, else the branch's push remote (5.3); honors `-C` (`~`, `$VAR`, `${VAR}` spelled out), `cd X &&`, chains (`&&`, `;`, `\|\|`, newlines); ignores heredoc data. base = `origin/<integration_base>` (missing → fail closed, 5.7) |
| `git push --delete`, `:dst`, `--tags`, `--dry-run`/`-n`, refspec `src` a tag with `dst` absent or under `refs/tags/` | pass | — |
| `git push <remote> <tag>:<branch>` (or `refs/tags/x:refs/heads/y`) | gate as a branch push | head = the tag's commit |
| `git push --all`/`--branches`/`--mirror` in a gated repo | deny | — |
| `gh pr merge` (`-R`/`--repo` before `pr`, between `pr` and `merge`, or after) | gate; deny without `--match-head-commit <sha>`; merge-preflight: no failing check (without `--auto` none pending) | head = sha, base = `origin/<baseRefName>` |
| `gh pr create` | warn: early warning (what the branch lacks) | current branch |

- One shell parser, `hooks/lib/hookkit/parser.ts` (the one parser, with the command model in `commands`, `steps`, `writes` and `variables`, and the git and `gh` argument readers in `gitargs`; the other `hookkit` modules are helpers such as `fields`, `text`, `paths`, `files`, `json`, `jsonout`, `errors`), serves ship-gate, git-guard, report-gate, env-preflight. ship-gate and git-guard share its push-argument reader, its `gh` subcommand reader, its `git config` reader (read or write, and the key named) and its path resolver (`-C`/`cd` directories and the files a command writes or reads: `~`, `$VAR`, `${VAR}` from the call's shell variables (plain and exported; a value is expanded when assigned, from the call's own variables and `$PWD` only) over the hook's own environment, `$PWD` as the step's directory). It follows wrappers (`env`, `timeout`, `nice`, `exec`, `sudo`), `-C`, `cd`, chains, `bash -c`/`eval` strings, `$(…)`, heredoc bodies, and reads git's dashed programs at a literal path (`/usr/libexec/git-core/git-push …`) as `git <subcommand>`, so git-guard's checks see them too. It reads past a wrapper option it does not know as a flag and records it as unattributable, as it does sudo's directory-moving `-D`, `--chdir`, `-R` and `-i`, so git-guard still sees the command (`sudo -i git push --force …`). A push or merge it cannot attribute to one repo and branch is denied `[K1]` in any repo (fail closed), ending with the exact command for the user's terminal (the whole call when a name is resolved at run time): a forwarder the parser keeps (`xargs`, `parallel`) or a wrapper carrying an unattributable option (`env --chdir=…`, `sudo -i`) whose wrapped words name `git`, `gh` or a shell (a dashed `git-push` too) or something resolved at run time, in a call that spells a push or merge anywhere (other programs, e.g. `echo`, `rm`, `grep`, and a `command -v` lookup pass), `gh api` that writes to an endpoint or GraphQL query resolved at run time (the query's text, a field named at run time: `-f "$KV"`, or a word that may expand to options: `gh api graphql $F`), `gh api` that merges or moves a branch (`…/pulls/<n>/merge`, `…/merges`, a non-GET call to `…/git/refs…`, a GraphQL `mergePullRequest`, `mergeBranch`, `enablePullRequestAutoMerge`, `createRef`, `updateRef(s)` or `deleteRef`), git plumbing that pushes without `git push` (`send-pack`, `http-push`, `subtree push`), a subcommand resolved at run time (`git $S`), a program resolved at run time (`$GIT`, `$CORE/git-push`, `"$(…)"/…`) in a call that spells a push or merge anywhere (its own path, an assignment, a loop list, another command's argument; `merge-base` counts, no exemption) or whose arguments make a `gh api` write, a push remote resolved at run time (`git push $R`, `"$R"`, `${R:-x}`, `$(…)`), a push target that is no remote of the clone, URL or existing path, `gh pr merge` naming no repo in a clone whose remotes name several repos with one gated (the user-run line adds `--repo <that repo>`), git aimed at another repository (`--git-dir`, `--work-tree`, `GIT_DIR`, `GIT_WORK_TREE`), a push whose routing config the clone does not hold when the gate reads it (`-c`/`--config-env` on a `remote`, `branch`, `url`, `push` or `include[If]` key, any `GIT_CONFIG*` variable, or, anywhere in the call, a `git config` write of such a key (option values such as `--file`/`--type` skipped; a write naming no key, e.g. `--edit`, counts; reads never count: `get`/`list`, a read option, or one name with no write option) or `git remote set-url|add|rename`; the user-run line is the whole call). `tests/fixtures/push-merge-spellings.tsv` (`command`, `expect` = `gate` \| `pass` \| `deny`) lists every tested spelling.
- Merging the integration branch moves `mb`: colleagues' files leave C, only files changed on both sides need re-review. Empty C → pass.

### 5.3 Gated-repos registry
`$KEEL_OVERLAY_DIR/gated-repos.tsv` ((h)): `origin gate integration_base risk_rules tests [push_approval [auto_merge]]`.
- `push_approval` `true` \| `false` (default; five columns = `false` everywhere): `true` where a branch push deploys or notifies; its pushes need approval like a merge.
- `auto_merge` `true` \| `false` (default; absent = `false`): `true` where review and tests are the whole merge bar. Every approval check passes without an approval record: `gh pr merge`, a `push_approval=true` push and the live fast-forward. Review and tests still apply. The optional columns come in order; a file may stop after any of them.
- `gate=code`: full model. `gate=smoke`: every push needs smoke evidence covering C, no review. `gate=off` or unlisted: pass.
- Repo key = `owner/repo` (lowercase, last two path segments, `.git` stripped, host ignored) of the repo the command changes. A push reaches every push URL of its remote (`git remote get-url --push --all`; 5.2), or its remote argument as a URL or a path from the clone's top level. Of several repos, a gated repo other than the clone's origin is judged first (deny `F-irreversible`: push from its own clone), then the clone's own gated repo, else the first. A remote resolved at run time, or one that is no remote, URL or existing path, is denied as unattributable. `gh pr merge`: `--repo`/`-R`, else `GH_REPO`, else the PR URL, else gh's default (`remote.<name>.gh-resolved`: the `owner/repo` it stores, or with `base` that remote's URL), else the clone's single remote repo (a stored value that names no `owner/repo` fails closed; a merge naming no repo is unattributable when the same call also runs `gh repo set-default <repo>` or a remote config change); several remote repos with one gated → deny unattributable with the `--repo` command to run. Other commands: origin. A repo's worktrees share evidence. No registry → all repos off (`outcome=warn` once per session).
- Intended: company code repos `code`; keel `code` (every path `standard` or `heavy`); keel-overlay `code` with settings fragments, data and prompt paths (`scheduled-tasks/`, `mcp/`, ledger, registry) `smoke-only` and code (`mods/`, `bin/`, `skills/*/scripts`) `standard`; the `~/.claude` data repo and personal repos `off`.
- A job touching only smoke-only paths runs `measure/smoke --candidate` from the worktree (`KEEL_OVERLAY_DIR` or `KEEL_HOME` = the worktree), `keel evidence write-smoke --repo <worktree>`, then pushes; after the merge the owner runs `bin/link --write` so the live data dir follows.

### 5.4 Risk classes
The gate recomputes risk from C; evidence never states it. Ambiguous → heavier.

| Class | Paths | Required |
|---|---|---|
| smoke-only | every C path matches a `smoke-only` rule | smoke evidence covering C |
| standard (default) | no rule matches | `lens-review` chain + tests; approval at merge |
| heavy | `heavy` rules (settlement, pricing, inventory writes, schema, batch, external contracts) | `lens-review` chain + tests; approval at merge |

- "At merge" = `gh pr merge`, plus `git push` where `push_approval=true`; no approval where `auto_merge=true`. Review and tests apply at both push and merge. Every chain link MUST be `lens-review` (a `single-lens` link → `[risk]` deny).
- Per path: a test path (segment `test`, `tests`, `__tests__`, or basename `test_*.py`, `*_test.*`, `*.test.*`, `*.spec.*`) adds nothing (alone: standard); else the repo set's heaviest matching rule; else standard. Push class = heaviest path, at least standard. smoke-only only if every path is; otherwise smoke-only paths count as standard but are no logic paths. A `light` rule is refused as an unknown class, so the gate fails closed until the overlay drops it (the class was retired by the 6.1 drop).
- Registry `tests=none`: every non-smoke push is denied "[K3] add test infrastructure first".
- K3: a logic path is a C path that is no test path or gitlink and classifies standard or heavy. Logic path with no test path → deny `[K3] logic changed with no test in the same range`, unless the chain head's `KEEL-EVIDENCE` ((d)) has `no_test_reason`, recorded on the pass line. A path whose change from its merge-base blob is a comment-only deletion is no logic path for this check. No logic path → no check.
- Comment-only deletion (`lib/evidence/comment_cleanup.ts`) of an old blob (merge-base, reviewed or evidenced) into a new one: same mode (`100644` or `100755`); a `.js`, `.ts` or `.java` file of at most 1 MiB (a `.py` file is none: Python is not run to prove it, so any `.py` change needs fresh evidence) that shrinks to a non-empty file; every comment of the old file, kept or removed, is non-empty (a bare `//` line makes the file no comment-only deletion), holds only letters, digits, `_`, whitespace and `.,!?()'"-` and none of the `PROTECTED` words anywhere, case-insensitive (notice and licence words, tool and linter directives, and words such as `ignore`, `command`, `global`, `region`, `generated`, `__`), so `// ignore empty rows` or `// note: x` makes the file no comment-only deletion; only comments on lines of their own are removed. A file the scanner cannot judge is none either; the exact list is `onlyCommentDeletions` and `slashComments`, and examples are text that is not UTF-8, a backtick in `.js`, `.ts` or `.java`, and in `.js` or `.ts` a `/` or `<` outside strings and comments (division, regex, generics, JSX).
- Tests and smoke evidence cover C when each C path has the same blob and mode in `git ls-tree <evidence.tree> -- <path>` (deleted = absent), or its blob is a comment-only deletion of that blob.
- Tests evidence also covers C when every C path is a non-deleted gitlink and, for each, the submodule's tests evidence (repo key from the `.gitmodules` url at the pushed head) has `head` equal to the pointer and `tree` equal to that commit's tree. A C that also changes a parent file still needs parent tests evidence covering all of C.
- Approval matches when `root_run_id` equals the chain's and `heads[<repo key>]` equals the chain head's `evidence_id`; a later delta moves the head and needs a new approval. One approval covers every repo of its root (submodule first, then parent; cross-repo), never another root.

### 5.5 Submodules
- A review over a parent with submodules writes one evidence per repo (one `KEEL-EVIDENCE` line per `diffs[]` item); blobs are per submodule, the parent sees gitlinks.
- "No commits in a parent repo" rules are overlay git-guard data.

### 5.6 Who writes evidence

| Kind | Writer | Provenance |
|---|---|---|
| review | report-gate at `PreToolUse[SubagentHandback]` (or `SubagentStop` without a hand-back that turn), when, after one leading `<<<KEEL-REPORT` line and one trailing `KEEL-REPORT>>>` line are dropped where present (trailing whitespace per line ignored, blank lines at either end dropped first, a marker line matched with its own whitespace trimmed), the report's line 1 is `VERDICT: PASS` or `VERDICT: NEEDS_FIXES` with ≥ 1 `KEEL-EVIDENCE:` line, each piped to `keel evidence write-review` | payload `agent_id`; `source.agent_transcript_path` as report-gate derives it ((g)). `write-review` refuses (3) without `agent_id` or when that file does not exist; it recomputes (blob, mode) from git object ids, never trusting a path list from the message |
| tests | `keel test -- <cmd>` | its `keel-tests.jsonl` line; 0 tests → none |
| smoke | `keel evidence write-smoke` after `measure/smoke` | its `keel-smoke.jsonl` line and tree |
| approval / ack | `keel approve <root_run_id> [--read]` in the user's terminal only; no gate reads ack | heads pinned at write |
| promote | `keel approve --promote <owner/repo> <sha>` in the user's terminal only | sha pinned at write |

- Reviewers never run a write command; lens-review ends with a reporter agent (plain text, no StructuredOutput) whose last message is the (d) report; a message that, after one leading `<<<KEEL-REPORT` line and one trailing `KEEL-REPORT>>>` line are dropped where present (trailing whitespace per line ignored, blank lines at either end dropped first, a marker line matched with its own whitespace trimmed), differs from the expected report on any line gets one more reporter dispatch naming the problem, and a second such message makes the run ERROR. Before that comparison the workflow drops a leading `[harness: …]` notice line and the blank line after it: Claude Code prepends it to the copy the workflow receives (not to the hand-back report-gate reads) when a report quotes instruction-shaped text such as `permissions.allow`.
- git-guard denies Edit/Write/NotebookEdit on `$KEEL_DATA_DIR/state/keel/**` and `$KEEL_DATA_DIR/logs/keel-fires.jsonl`; Bash writing or removing one of those (target resolved like a `cd` target: `~`, `$VAR`, `${VAR}` from the call's shell variables (plain and exported; a value is expanded when assigned, from the call's own variables and `$PWD` only) over the hook's own environment, `$PWD` as the step's directory, relative to the step's directory); Bash running `keel approve` or `keel evidence write-review`.
- `[F-hookskip]` git-guard denies: `claude … --settings '<inline JSON>'` with `disableAllHooks` unless that call disallows Bash, Edit and Write; an Edit/Write, or a Bash write whose call text spells it, setting `disableAllHooks` in `.claude/settings*.json`; `git commit|merge|push --no-verify`, `git commit -n`, `git -c core.hooksPath=…`, a `git config` write of `core.hooksPath` (reads pass); writes to `logs/keel-fires.jsonl`; a change to keel's links or the installed plugins: a word that resolves against the call's directory to `…/bin/link` or `…/bin/link.ts` (any case) with `--write` or `--unlink` after it (a dry run, `--check` and `--help` pass), and any `claude plugin` or `claude plugins` subcommand other than `list`, `validate`, `help`, `details`, `eval` and `marketplace list|help`, whatever plugin it names (`-h`/`--help` passes).
- `[C-isolation]` git-guard denies Edit/Write/NotebookEdit, plain Bash writes and git subcommands moving index, HEAD, a branch or the working tree (checkout, switch, restore, reset, add, rm, mv, commit, cherry-pick, revert, am, apply, merge, rebase, pull, stash, clean) under the live checkouts (realpath of `KEEL_HOME`, `KEEL_OVERLAY_DIR`), not their worktrees; git is judged in its `-C`/cwd directory; a write after a `cd` the hook cannot resolve is judged where the call starts and the message says so; a write target whose own variables stay unresolved passes; the message prints `git worktree add` and the user-run `git merge --no-ff refs/heads/<branch>`.
- F-attribution also scans every heredoc of the Bash call, files given to `gh pr create|edit|merge --body-file`, `gh pr merge --subject/--body`, and the pushed commits (`<source> --not --remotes`; `--all`/`--branches`/`--mirror`: `--branches --not --remotes`). F-secrets also scans Write/Edit/NotebookEdit content and staged commit content for known values from overlay `git-guard/known-values.tsv` ((h)), built at runtime: values of 6+ characters, never logged or printed; a hit names `file:line` and the key. It scans commit messages and PR text for known values the same way F-attribution reads them: the call's heredocs, `-m`/`--message` words and `-F`/`--file` files (read from the `git -C` directory) of a commit, and the arguments and `--body-file`/`-F` files of `gh pr create|edit|merge`; those hits name the source (`commit message`, `PR text`) and the key without a line. While a known-values list is loaded, a message or body given any other way is denied with the `procedural` F-secrets message and the step to write it to a file and pass a plain `-F <path>` (gh: `--body-file <path>`): stdin (`-`, `/dev/stdin`), a file the hook cannot read yet, a word holding `$`, a backtick or a backslash-newline inside quotes, an abbreviated `--message`/`--file`, or the flag inside a short-flag cluster (`-am`, `-Fmsg`, gh `-dF`; any gh PR word that starts with one dash and holds `F`, such as `--title -Fix`, counts as one). Otherwise a deny then ends with ask-the-user instead of run-yourself unless the command is plain call text (only letters, digits, whitespace, quotes, `_.,:;=@%+-/` and `&&`), names no message file, gives its message in a plain form, and holds no value in its own text or its shell-parsed words; this holds on the normal path and when the guard fails closed. A commit that stages in its own call (`git add … && git commit`, `commit -a`, `commit <paths>`, `--pathspec-from-file`) is checked on what it would contain: the hook copies the repo's index to a temporary file, replays the call's `git add` steps and the commit's own staging on the copy with `GIT_INDEX_FILE`, runs the path rules, the secret scan and the known-value check on it, and removes the copy; only staging it cannot replay (interactive or patch staging, a run-time expansion or unresolved directory in the `git add`, a `git add` that fails on the copy, or any step before the commit other than a `git add` in the same repository: replay needs the call text to hold only letters, digits, whitespace, quotes and `_.,:;=@%+-/`, with steps joined by `&&`, `;` or a newline, so a `cd`, `pushd`, `export`, background `&` or any program before the commit counts; use `git -C <dir>`) denies with the `procedural` F-secrets message. The copy keeps the index file's timestamps, so git's racy-entry check still catches an edit made in the same second as the last index write.
- A missing expected payload field → `outcome=contract-miss` (detail: `cc_version` first, then missing fields, context and keys received, so the 200-character limit cuts the tail and never the version), behavior unchanged. report-gate expects `tool_input.message`, `agent_id`, the derived transcript (hand-back); `agent_id`, `agent_transcript_path`, and `last_assistant_message` unless the transcript holds final text, the report was handed back (the turn state records it, or the transcript ends with a `SubagentHandback` call and the payload carries no final text) or the agent used `StructuredOutput` (SubagentStop); a SubagentStop whose only missing field is `last_assistant_message`, with no readable transcript and an empty or absent `agent_type`, logs a K2 `warn` naming `agent_id` instead; a SubagentStop miss also names `agent_id`, `agent_type` and the agent's last tool, ahead of the keys. ship-gate: `tool_input.command` (Bash).

### 5.7 Failure mode
- ship-gate error on a push or merge in a `gate=code` or `gate=smoke` repo, or before its repo is known while any registry row is gated → deny; otherwise pass. A crash while the call may push or merge (a push or merge word anywhere, a push or merge spelled without one (`send-pack`, a REST `merges` or `git/refs` endpoint, a GraphQL merge or ref mutation), or `git`/`gh` beside a name resolved at run time, so `gh api …/pulls/N/merge` and `S=push; git $S` count) → deny. A crashed or timed-out process: `onFailure:"block"` ((g)).
- ship-gate at `Stop` (main session only, no `onFailure`): when the session's cwd repo has a HEAD its upstream does not hold, it runs the push judgment of `keel evidence check` with the approval requirement left out (waiting on `keel approve` is the normal resting state) and, if a reason remains, returns it once as Stop `additionalContext`, which continues the turn one round; `stop_hook_active` passes, the same session, repo, HEAD and reasons are told once (`state/keel/sessions/<session>.stop-readiness`), and each reminder writes one `warn` fire (never a deny, so no `fires:` metric counts it). Any error passes, with the reason on stderr. Only the cwd's repo is judged.
- ship-gate at `Stop` also checks the advisor call, as a K1 enforcement point: the advisor is a separate context judging the turn's work before it ends. It reads the main transcript (`isSidechain` entries skipped). The advisor counts as available when the latest `advisor_tool` attachment says `available: true`. The turn starts at the latest `type: "user"` entry whose `origin.kind` is `"human"`, so compaction summaries, task notifications and tool results do not start a new turn. When the advisor is available, the turn edited a file (Edit, MultiEdit, Write, NotebookEdit) or made six or more tool calls, and no `server_tool_use` named `advisor` appears since that prompt, it returns Stop `{"decision":"block"}` with one `block` fire, which `fires:K1` counts; an unready-push reminder for the same Stop rides inside that block. `stop_hook_active` passes, so it blocks at most once per stop. No transcript path, no recorded owner prompt or no available advisor passes; an unreadable transcript passes with the reason on stderr.

### 5.7a Threat model
- Hooks stop an honest agent's mistakes and shortcuts written as commands normally are; an unattributable spelling is denied, not guessed (5.2).
- Deliberate evasion is out of scope: a parser over arbitrary shell cannot be complete. Accepted gaps: every spelling §10 removed; a program name or script built so the call spells no push or merge (`$(echo … | base64 -d)`, `bash p.sh`, a symlink); a main thread briefing a rubber-stamp reviewer (the gate cannot tell who authored a diff).
- Final guard: branch protection on integration branches (required PR, review, status checks) binds every author; a gated repo without it has a gap in that repo, not in keel.

## 6. Measurement

- `measure/weekly`: repo-layer rules; always-loaded bytes (generated CLAUDE.md; sum of MEMORY.md indexes, apart); post-deploy defects; keel core non-test lines of code and `docs/DESIGN.md` bytes (no cap; unexplained growth is an incident). `review_rounds`: over live review evidence, the count of (repo, root) chains, of chains whose root review was NEEDS_FIXES, and of chains per number of NEEDS_FIXES links; an unreadable review file gives `{"error"}` in its place. `review_tokens`: the tokens the lens-review workflow runs of live review evidence spent, per root (a root's reviews in every repo), so a NEEDS_FIXES round has a measured price. Each review's run is the `wf_*` directory under `subagents/workflows` that holds its `source.agent_transcript_path`; every `agent-*.jsonl` in it counts, each `message.id` once by its last line (a streamed message repeats with growing counts), a usage `iterations` list counts per iteration under that iteration's model (an advisor call spends tokens the top-level usage leaves out), and a run shared by two repos' evidence counts once. It reports `roots`, `by_model` (input, cache creation, cache read and output tokens per model, no prices; a model that spent nothing is not listed) and `by_needs_fixes_rounds` (roots and tokens per NEEDS_FIXES links of the root's newest chain, the most of any repo; a superseded head's tokens count too, since they were spent), and `unmeasured`, the roots with a review that names no workflow run (no transcript, a plain subagent) or whose run is gone, unreadable or holds no usage; those roots count nowhere else. Authoring, fix work and the comment pass are not in it. An unreadable review file gives `{"error"}` in its place. `harness_versions`: the Claude Code versions the harness-contract fixtures record (`tests/hooks/fixtures/harness-contract/*.jsonl` under keel home), the count of live reviews' agent transcripts (`source.agent_transcript_path`, each path once) per the last version each one carries, the observed versions newer than the newest recorded one (segments compared as numbers, so 2.1.309 is newer than 2.1.99), and `unversioned`, the named transcripts that are gone, unreadable (not UTF-8, a directory, no permission) or carry no version; a version in `unrecorded_newer` means report-gate runs on a transcript shape no contract test has seen, so record a fixture for it. ### 6.1 Risk pilot exit criteria (pre-registered)
The two-week post-swap pilot decides `risk`. The user confirms or changes these numbers before the first piloted ship; the commit setting them predates the first fires line with a `risk` value. `run:risk` reports every input.
- Inputs per class: ships (`pass` lines), escaped defects traced to the ship's class (§6), rework (lines shipped and changed again within 14 days, from git, refactor-only commits excluded), median chain-head PASS → approval time. Baseline: the previous harness's last 60–90 days in the same repos, re-classified by the same function, labelled historical.
- How `measure/metrics/risk` reads them: a ship is one `(repo, head)` among `risk` `pass` lines; its count is the classified ships, so the row's status follows the ships alone. A refactor-only commit is one whose subject starts with `refactor`, `rename` or `move`; rework is shipped first-parent lines blamed at the ship's head minus those still blamed to them on `origin/HEAD` 14 days later, with refactor-only commits ignored. The ship's commits come from git, since review evidence expires before the horizon: a head merged into the default branch starts at the merge base with the merge's first parent, and a fast-forwarded head starts at the nearest commit on its first-parent chain, down to the repo's latest earlier shipped head on that chain, from which the diff to the head has the pass line's `files` and `lines` (the push's diff stat; a pass line without them starts at that earlier head), so commits that were never pushed through the gate are not the ship's. A rename within the 14 days is followed, so moved lines are not rework. Any surviving review evidence of the repo names the local checkout. A decided ship's numbers are final, so they are kept in `state/keel/metrics/risk-rework.json` (`{"version", "ships"}`) by repo and head, written as each ship is decided so a run stopped later keeps them, and not recomputed; a file of another `version` is ignored, and the version is raised whenever the way a ship is computed changes (2: the diff-stat bound); pending and not computable ships are not kept, and a file it cannot read or parse is ignored. A ship under 14 days old is pending, and an older one is listed as not computable with its reason when it has no head, no local checkout holds it, the checkout has no `origin/HEAD` or has not seen the default branch past the horizon (neither a tip commit after it nor a `FETCH_HEAD` in any of the repo's worktrees written after it that lists the default branch fetched from origin's URL), the head is not on the default branch or reached it after the horizon, or no earlier ship bounds a fast-forwarded head, or no base on that chain matches the pass line's diff stat. A review or approval evidence file it cannot read is skipped and counted in the top-level `unreadable_evidence`. Review-to-approval uses the run's first approval and counts ships whose approval or review evidence has expired as `no_approval_evidence`. Escaped defects come from the overlay runners named `defects-*` (each prints `{"count","items"}`; an item is `{repo, commit, ts, kind, offending, traced_by}` with full shas): items are deduplicated by repo (case-insensitive) and fixing commit across runners; each offending sha is traced, in the repo's local checkout, to the earliest of all the repo's ships (not only those in the window) whose head contains it, and the item counts once, for the earliest ship over all its shas, in that ship's class when the ship is in the window. An item that reaches no ship (no checkout, unknown sha, no containing head) is listed in `untraced_defects` with its reason, never dropped. Both keys are top-level keys of the runner's output that `measure/run` carries through (any extra top-level key of a `run:` runner is, with `count` and `items` unchanged). A runner that fails or prints an item off the contract is named with its error in `defect_sources`, never counted as 0; with no `defects-*` runner, or none that ran, each class item says `no source`. The baseline is deferred and each class item says so instead of reporting 0.
- **extend** (never keep): < 8 light or < 5 standard ships; two more weeks.
- **keep** (`risk` → charter): 0 escaped light defects; light rework ≤ standard + 5 percentage points; light median review-to-approval below standard's.
- **adjust**: exactly 1 escaped light defect, or light rework over the bound with 0 escaped; move the path rules behind the misses one class heavier, two more weeks.
- **drop** (retire `risk`, all pushes standard): ≥ 2 escaped light defects, or light review-to-approval not below standard's.
- Each later relaxation of a class is its own user-approved ledger change.
- **Result (2026-11-14): drop.** `node measure/run.ts risk`, 60-day window, 396 ships: light 33 ships, 1 escaped defect, rework 39.6 % over 7 decided ships, median review-to-approval 2 min; standard 347 ships, 4 escaped, rework 23.6 %, 2 min; heavy 14 ships, 0 escaped, 3.5 min; smoke-only 2. Defect sources: `defects-hotfix` 0, `defects-reverts` 5, 0 untraced; baseline deferred. Light review-to-approval was not below standard's, so the owner chose drop: `light` is retired, its paths and test-only pushes class standard (K3 same-range test or `no_test_reason`, and test evidence even where it was skipped), and heavy and smoke-only stay; `measure/metrics/risk` still reports `light` for ships recorded before the drop.
- **Correction (2026-11-26).** The light rework in the result above is wrong: 39.6 % came from one fast-forwarded ship, `3901955c` (pass line: 1 file, 74 lines), whose base was the repo's earlier ship and so took in 28 commits it never pushed; without it light rework is 7.1 % (both figures from the 2026-11-26 measure audit, not from a rerun of the bounded runner). The base is now bounded by the pass line's diff stat (above). The drop stands: it rested on light review-to-approval not being below standard's and on the escaped light defect, not on rework. This correction covers only the light rework figure; the other numbers of the result are unchanged.

## 9. Compatibility

Relied-on Claude Code behaviors; a change is contract drift, logged by report-gate and ship-gate as `outcome=contract-miss` with `cc_version`:
- Payload fields as in (g); `agent_id` only inside a subagent; `SubagentHandback` carrying the full subagent report in auto mode.

- A missing registered script makes `node` exit 1, which does not block: the fail-open hooks (report-gate, model-assign, env-preflight) fail open, and ship-gate and git-guard still block through `"onFailure":"block"`; `link --check` and smoke `dangling` catch it.

It writes no fires: no ledger row owns it. A missing `PRINCIPLES.md`, or either file failing to read for another reason, injects a line naming the cause and telling the session to tell the owner; a missing `PERSONAL.md` is left out.
- Mod tool calls (Claude Code 2.1.321): a mod's own `$.tool.call` and `$.mcp.call` raise no permission prompt, so `permissions.ask` gates only Claude's calls; `permissions.deny` and organization policy still apply to a mod. What a mod may call is therefore decided by deny rules and smoke `mod-trust` (`reviewed-mods.txt`), not by ask rules.
- Auto mode and `updatedInput` (Claude Code 2.1.325, Desktop): the server-side auto-mode classifier reviews a call as the model wrote it, so a PreToolUse `updatedInput` makes the CLI deny the call as unreviewed (`server_input_rewritten`, PermissionDenied reason `Classifier unavailable`); a brief too long to quote is rewritten again on retry and denied again. model-assign therefore denies in auto mode and lets the model name the values.
- Monitor commands (Claude Code 2.1.314): a PreToolUse hook with a `Bash` matcher (`Bash`, `Bash|Edit|Write|NotebookEdit`) also runs on shell commands started with the Monitor tool and receives them as a Bash call; its deny and ask apply, its allow and `updatedInput` do not. ship-gate, git-guard and the spring-maven env-preflight (`stacks/spring-maven/settings.json`, `if: Bash(*mvn*)`) only deny or add context, never allow or rewrite, so they cover Monitor commands with no Monitor matcher; a hook that must rewrite or allow a Monitor command needs a matcher that includes Monitor (`Bash|Monitor`, `.*` or none), and any `if` on it must name Monitor (`Monitor(tail *)`).

### (c) Evidence

Path: `$KEEL_DATA_DIR/state/keel/evidence/<kind>/<owner>__<repo>/<evidence_id>.json` (review, tests, smoke, promote) or `…/evidence/<kind>/<evidence_id>.json` (approval, ack). Dirs 0700, files 0600, atomic write (temp + rename), never modified.

`evidence_id` = `<kind>-<YYYYMMDDTHHMMSSZ>-<8 hex>`; `run_id`/`root_run_id` match `^[A-Za-z0-9._-]{8,64}$`; shas and tree ids 40 hex; timestamps UTC `YYYY-MM-DDTHH:MM:SSZ`. All kinds: `schema` (1), `kind`, `evidence_id`, `created_at`, `expires_at` (+ 30 days for review, approval and promote; + 14 days for tests, smoke and ack).

| Kind | Additional keys |
|---|---|
| review | `repo`, `repo_root`, `run_id`, `root_run_id`, `since` (previous review `evidence_id` or null), `since_tree` (or null), `review_base`, `head` (sha or null), `snapshot_tree` (or null), `reviewed_tree`, `review_kind` (`lens-review` \| `single-lens`), `verdict` (`PASS` \| `NEEDS_FIXES`), `no_test_reason` (string or null, (d)), `paths` (`[{"path","blob"(null = deleted),"mode"}]`, deleted mode `000000`), `source` (`{"session_id","agent_id","agent_type","transcript_path","agent_transcript_path","via":"SubagentHandback"\|"SubagentStop"}`) |
| tests | `repo`, `repo_root`, `run_id`, `head`, `tree`, `cmd` (argv list), `exit` (0), `count`, `framework`; `superproject` (the origin `keel test` ran from) on a submodule's evidence only |
| smoke | `repo`, `repo_root`, `run_id` (smoke run), `tree` |
| approval, ack | `root_run_id`, `heads` (`{"<owner/repo>": "<review evidence_id>"}`), `source` (`cli`), `session_id` (null) |
| promote | `repo`, `head` (the develop sha the promote merges), `source` (`cli`), `session_id` (null) |

The gate ignores expired evidence. `keel evidence gc` deletes expired files; ship-gate runs it at most once per 24 h (stamp `$KEEL_DATA_DIR/state/keel/gc.stamp`), failures ignored. The same run bounds the node compile cache (`lib/evidence/compile-cache.ts`): it removes every `state/keel/node-compile-cache/<version>` folder whose name does not start with the running node's `<process.version>-<process.arch>-`, then removes the rest as well when those folders together hold more than 64 MiB of file content, and records `compile cache removed <files> files <bytes> bytes` only when it removed something. Before the decision is emitted it only walks the folders (about 1.2 s for 132,000 files) and renames each doomed folder to `removing-<ms>-<name>`; a detached node process deletes the renamed folders (about 11 s for 132,000 files), and a later run finishes any it left behind. The limit counts file bytes, not disk blocks (about 1.6 times more on the owner's machine), and the cache can grow by the writes of one gc interval past it: the peak is 64 MiB plus a day's writes (about 285 MB on the heaviest measured day).

### (d) Reviewer report format

```
VERDICT: PASS
<findings, notes; MUST include a `git diff --stat` summary line such as "3 files changed" so report-gate's K2 check sees evidence>
KEEL-EVIDENCE: {"v":1,"repo_root":"/abs/repo","review_base":"<40hex commit>","head":null,"snapshot_tree":"<40hex tree>","since":null,"run_id":"rv-…","root_run_id":"rv-…","review_kind":"lens-review"}
```

- Line 1 is exactly `VERDICT: PASS` or `VERDICT: NEEDS_FIXES` (trailing whitespace ignored); else no evidence.
- One `KEEL-EVIDENCE: ` line per repo: single-line JSON with exactly `v, repo_root, review_base, head, snapshot_tree, since, run_id, root_run_id, review_kind`, optional `no_test_reason` (one line; the only K3 escape besides a comment-only deletion, 5.4; lens-review emits it for a repo when the tests-lens auditor returns a non-blank `no_test_reasons` entry for that repo_root, joined to one line; a reason from another lens is ignored; in a delta the tests auditor is also given the whole `review_base`..end range, because K3 reads the reason from the chain head for that whole range). Optional `fix_delta` (literal `true`), which lens-review emits when the run carried `priorFindings` and so judged with the high-only bar: `write-review` refuses (3) a `fix_delta` with `since` null or with the review at `since` not `NEEDS_FIXES`, and refuses a `lens-review` delta without `fix_delta` whose `since` review is `NEEDS_FIXES`, so a fix is never judged as a delta after a PASS. It is not stored; the parent's verdict is. Exactly one of `head` / `snapshot_tree` non-null. `review_base` = the merge-base sha diffed from; `since` = the tree a delta diffed from, else null; lens-review's prepare fails when `since` is not a tree object. Root: `root_run_id == run_id`.
- Lenses read diffs against the snapshot tree id (`keel snapshot`), never the live working tree.
- lens-review args: `runId` (optional; default `rv-<UTC stamp>-<6 hex>`), `rootRunId` (required when any diff has `since`); unknown keys rejected (no free-text `context`). Briefs carry no author claims: `requirement` (the request as stated) to every lens, labelled not evidence; `readingGuide` only to the writing-readable-code lens (appended to a caller-supplied one), labelled claims to check; caller `guardrails` to every lens and the verifier. `readingGuide` or `guardrails` text asserting its own correctness (tests pass, LGTM, "we verified", works correctly, …) fails the run before any agent starts; `requirement` is the user's request, so a goal it states is not screened.
- A merge-blocking (high/medium) finding carries a `repro`: command or input with observed and expected result, or `static: <what> at file:line`. The verifier runs command repros; one not showing the failure refutes the finding. No repro → non-blocking (`no repro`).
- Each finding and each verifier decision may carry `origin` (`introduced` | `pre-existing`, judged against `git show <review_base>:<path>`). Only when both say `pre-existing` is the finding listed under `Pre-existing (present at the review base; not merge-blocking)` and left out of the verdict; otherwise it is introduced.
- `keel review prepare` also prints `needs_fixes_rounds`: the NEEDS_FIXES links in the newest recorded chain of the request's `rootRunId` (0 without one). lens-review adds this review when it is NEEDS_FIXES, returns the sum as `needsFixesRound`, and when this review is NEEDS_FIXES and the sum is 3 or more adds `Step back: NEEDS_FIXES round <n> on root <root_run_id> (cap 3). …` after `Refuted`. The verdict is unchanged; a missing or non-integer count is 0.
- A PASS report adds `Owner approval, in your own terminal once the tests are green: keel approve <root_run_id>` after `Refuted`, so the owner can copy the command. The workflow never runs it; git-guard still denies an agent's `keel approve`.
- `keel review prepare` also prints `risk_class`: the heaviest tier (`risk.classify` with the repo's gated row and risk rules) across the reviewed diffs, or null when any repo has no gated row. lens-review sets audit and verification effort from it: `medium` for smoke-only and standard, `low` for a non-heavy root diff of at most 2 files and 10 changed lines, `high` for heavy, null or an unknown value; an explicit `effort` wins. The result returns the chosen `effort`. Without `prepared`, the prepare agent also runs `keel review prepare` on the diffs and copies its `risk_class` (`none` when null, empty when the command fails), so the same tiers apply.
- Every report value is one line: a `repo_root` with a quote, control or line-separator character is rejected; agent text and lens keys are flattened.

`bin/link`:
- `--write` refuses (3) when `settings/core.json` or a declared fragment is missing, a target is a real file or foreign link, or owned keys drifted since the last write (hash in `$KEEL_DATA_DIR/state/keel/link-state.json`) unless `--force`. Without `link-state.json`, owned keys differing from the live ones exit 3 unless `--adopt`, which prints every item it would drop (each `permissions.allow/deny/ask` entry, `defaultMode`, each env key as `env <NAME> (removed)` or `env <NAME> (value changed)`, never its value, every live hook entry whatever its type, compared by (event, matcher, full hook object), labelled `hooks.<event> <command>` for command hooks) and refuses unless all are in `--accept-drops <file>` (one listed line per line, verbatim; blank and `#` lines skipped). The dry run lists the same lines under `dropped`. A refused `--write` prints the drops before its blocking problems and, unless a problem no flag lifts remains, the `--write` that lifts them all (`--adopt`, `--force`, `--accept-drops <file>` as needed, and `--allow-worktree` when this run was given it). Each settings write first copies `settings.json` to `state/keel/link-backup/<ts>-<pid>/settings.json` (0600). `--force` moves a non-keel CLAUDE.md to `link-backup/<ts>-<pid>/CLAUDE.md`; `link-state.json` records the first such move. It sets `git -C $KEEL_HOME config core.hooksPath githooks`.
- `--plugin` switches to plugin mode and `--full` back to the link install; both go with `--write` or the dry run, and `link-state.json` records plugin mode (`"mode": "plugin"`; absent = full), so a plain `--write`, the dry run and `--check` keep the recorded mode. Plugin mode leaves to the keel plugin what it provides: keel-manifest links to `skills/*`, `agents/*.md` and `workflows/*.js` that are keel links are removed (`remove-link`, problem `provided-by-plugin`), a foreign link or real file there is left alone, and `bin/keel`, `workflows/review-lenses.json` (read from the data dir by `keel review prepare`) and every overlay-manifest entry stay; a generated CLAUDE.md is removed (`remove-claude-md`) and none is written, while a recorded moved-aside CLAUDE.md stays for `--unlink`; `settings/core.json` contributes no hooks but keeps its permissions and env. The ledger wiring check and the gate `onFailure` check read the merged settings plus the registrations in `hooks/hooks.json`, matched by hook script name; a gate problem names the file its registration came from: `hooks/hooks.json` for a plugin registration, the core, stack or overlay fragment for a merged one, in either mode. A refused write prints the command to run once reviewed with the `--plugin` or `--full` flag it was given. Plugin mode needs live `enabledPlugins` `"keel@keel": true`; without it, `plugin-not-enabled` blocks every `--write` and fails `--check`, so the core hooks never leave settings.json while no plugin runs them.
- A target under `scheduled-tasks/` is written as a regular copy of its source, never a symlink (the desktop app refuses to open a symlinked task file and skips the run). A keel link there is replaced by the copy; a copy that differs from its source (`copy-drift`), a foreign link or a directory there exits 3 unless `--force`, which moves it to `link-backup/<ts>-<pid>/<target>` first. `--unlink` leaves copies in place.
- `--unlink` removes only links into `KEEL_HOME`/overlay and a generated CLAUDE.md with a matching header, deletes `link-state.json`, and treats settings.json as recorded there: puts the owned keys (`hooks`, `permissions`, `env`) of the backup from before keel's first write into the live file, an owned key the backup lacks removed, while the other keys keep their current bytes and order, as `--write` keeps them (`restore-settings`); if that write created the file, removes the owned keys and keeps the rest (`remove-owned-settings`); a live file that is not a JSON object gets the whole backup back (`restore-settings`), or stays untouched when that write created it; no record or no live file → untouched. It moves the CLAUDE.md recorded as moved aside back when that copy still exists and no CLAUDE.md is in its place (`restore-claude-md`, with `from`); otherwise it only removes the generated one. Before touching settings.json it saves the live file to `link-backup/<ts>-<pid>/settings.before-unlink.json` (0600).
- `--check` also reports a gate registration lacking `onFailure:"block"` or a numeric `timeout` (`gate-onfailure-missing`), an active `layer=hook` row whose `enforced_at` hook is unregistered in the merged settings (`hook-unregistered`), `core.hooksPath` drift (`hookspath-drift`).

`rule-checks.ts`: signal-only regex checks over the diff's added lines (v1 rule-checks without company lenses); a signal is a candidate the lens judges. Test paths (the 5.4 set) raise no line or size signal and do not count toward the diff signal; git output is decoded as UTF-8 with replacement. `--head <commit>`: merge-base(base, head) → head; `--head <tree>` (a `keel snapshot` tree): `--base` as given (the review's `review_base`) → that tree via `git diff-tree`, scanning exactly the reviewed content; no `--head`: merge-base(base, HEAD) → working tree plus untracked files. Submodules whose gitlink changes are scanned recursively; a changed gitlink whose submodule is not checked out is scanned old→new pin in the first `--module-repo` holding both commits (only with `--head`), otherwise it is `blocked`. lens-review passes the other reviewed repos as `--module-repo`. Output (not JSON): zero or more `signal <ID> <file:line> <text>` lines, then exactly one last line `summary repos=<n> scanned_lines=<n> signals=<n> unscanned=<csv|none> blocked=<csv|none>`. `<ID>` is always `K5.<n>` (n = R-number), never `R<n>` or v1 `T<n>`; `<file:line>` relative to `--repo` (submodule paths prefixed) or `(diff)` for a whole-diff signal; `<text>` ≤ 160 chars. Exit 0 = scanned; 2 = usage error, crash (`blocked=.(crashed: <ErrorType>)`) or any repo unscanned (`blocked` ≠ `none`), which the lens reports as a finding, never clean. lens-review counts its built-in rule-checks lens as not run (NEEDS_FIXES) unless the lens notes quote exactly one `summary` line per reviewed repo, each `blocked=none`.

K4 grading (`measure/evals/eval K4`): `claude -p` disables the AskUserQuestion tool, so each run appends one system prompt line (`--append-system-prompt`, evalkit runner QUESTION_PROTOCOL) asking the model to put each question for the user on its own line starting with `QUESTION:`. A run asks when it calls the ask tool, when a line outside fenced code starts with `QUESTION:` (after any run of the prefixes `-`, `*`, `+`, `>`, `#` or a number followed by `.` or `)`, then optional `**` or `__` bold), or when a `# Refined request` heading (the refining-requests brief) appears; it answers when the expect token appears outside fenced code before the first `QUESTION:` line (a follow-up question may come after the answer; options under a question are not an answer). No language-specific phrases: the marker is the same whatever language the model replies in. The protocol line is identical for the v1 baseline and keel runs.

smoke checks (kind × scope): ledger-format, id-unique, caps (each), id-tagging (principles, personal, each skill; 0 rule lines checked across all skills = FAIL), fires-rule-ids, contract-miss-cap (more than 20 `contract-miss` fires lines dated today or yesterday FAILs, naming the count per hook), rule-of-two, metrics (every `run:` runner of the rows starts before the rows are judged, at most 6 at a time, each with its own 120 s timeout, after which the runner is killed with its whole process group; rows are then judged in ledger order, so the assertion is the one a sequential run prints), expiry (WARN), boundary (keel tracked files; missing or empty lexicon FAILs), link-integrity (`bin/link --check`, incl. the CLAUDE.md cap; with `--candidate` instead the link tool's dry run with `KEEL_DATA_DIR` = a fresh empty temp dir (removed after) and the same `KEEL_HOME`/`KEEL_OVERLAY_DIR`, FAIL on any problem other than those an empty data dir always has: `link-missing`, `copy-missing`, `settings-drift`, `claude-md-drift` "generated CLAUDE.md is missing"; a refused or crashed dry run FAILs), wired-fires, dangling (symlinks in `$KEEL_DATA_DIR/{skills,commands,agents,workflows,bin,mcp}`), mod-trust, assertion-cap.

### (g) Settings fragments and hook registration

A fragment is a JSON object with only `hooks`, `permissions`, `env`, in Claude Code settings shape. Strings may use `{{KEEL}}` (KEEL_HOME), `{{OVERLAY}}` (KEEL_OVERLAY_DIR), `{{DATA}}` (KEEL_DATA_DIR), expanded by `bin/link` to absolute paths; any other `{{…}}` is an error. Order: `settings/core.json`, `stacks/<name>/settings.json` per overlay `stacks.txt` name (sorted), overlay `settings/*.json` (sorted). `hooks.<event>` arrays concatenate; `permissions.allow|deny|ask` concatenate, first occurrence kept; other `permissions` keys and `env` keys: later wins, conflicts reported. The result replaces the owned keys of `$KEEL_DATA_DIR/settings.json`; other keys and their order stay byte-identical; atomic write.

```json
{"hooks":{"PreToolUse":[{"matcher":"Bash","hooks":[{"type":"command","command":"node {{KEEL}}/hooks/ship-gate/ship-gate.ts","timeout":60,"onFailure":"block"}]}]}}
```

| Hook | Event | Matcher | Command | Timeout | On own error | On process failure |
|---|---|---|---|---|---|---|
| ship-gate | PreToolUse | `Bash` | `node {{KEEL}}/hooks/ship-gate/ship-gate.ts` | 60 | 5.7 | `"onFailure":"block"` |
| git-guard | PreToolUse | `Bash\|Edit\|Write\|NotebookEdit` | `node {{KEEL}}/hooks/git-guard/git-guard.ts` | 10 | 5.7 | `"onFailure":"block"` |
| report-gate | PreToolUse | `SubagentHandback` | `node {{KEEL}}/hooks/report-gate/report-gate.ts` | 30 | 5.7 | fail open (ship-gate K1 already denies without evidence) |
| report-gate | SubagentStop | — | same | 30 | 5.7 | fail open (SubagentStop ignores `onFailure`) |
| model-assign | PreToolUse | `Agent\|Workflow` | `node {{KEEL}}/hooks/model-assign/model-assign.ts` | 10 | 5.7 | fail open |
| env-preflight | PreToolUse | `Bash`, `"if": "Bash(*mvn*)"` | `node {{KEEL}}/stacks/spring-maven/hooks/env-preflight.ts` | 10 | 5.7 | fail open |

- Every command runs node with `NODE_COMPILE_CACHE="${KEEL_DATA_DIR:-$HOME/.claude}/state/keel/node-compile-cache"` before the `node {{KEEL}}/…` shown above; the cached compile saves about 30 ms per hook start. The cache is bounded by the daily ship-gate gc (section (c) Evidence): other node versions' folders are removed, and the current one is removed whole when over 64 MiB, the cap sitting well above the 3.9 MiB one checkout's tests compile; a node process that finds its cache folder gone skips the cache write and the next start recreates it. The env-preflight `if` rule keeps Claude Code from starting the hook for a call that never names `mvn`, the same test the hook itself applies first (`commandLine.includes("mvn")`); a call Claude Code cannot split still starts it.
- "On process failure" = Claude Code's action when the hook process crashes or times out. Only the two gate registrations carry `"onFailure":"block"` and an explicit `timeout` (else `link --check` `gate-onfailure-missing`); a broken blocking gate blocks every matching call, and the way out is the user's terminal.
- Each registered `timeout` exceeds the longest subprocess budget in that hook: git-guard gives each git call and the boundary scan 8 s; ship-gate gives each git call and fetch 20 s and `gh pr view` 12 s (`keel snapshot` and `keel test`, which no hook runs, give each snapshot git call 300 s); a merge path that still runs past its 60 s is killed and `onFailure: block` denies it; each hook's test reads the registered timeout from `settings/core.json`.

Hook protocol:
- stdin = one JSON payload: `session_id, transcript_path, cwd, permission_mode, hook_event_name`; `agent_id, agent_type` only inside a subagent; PreToolUse adds `tool_name, tool_input, tool_use_id`; SubagentStop `agent_id, agent_transcript_path, agent_type, last_assistant_message, stop_hook_active`. Inside a subagent `transcript_path` is the MAIN session's.
- report-gate at `PreToolUse[SubagentHandback]` reads the report from `tool_input.message` and MUST derive the agent transcript as the first match of `<dirname(transcript_path)>/<session_id>/subagents/**/agent-<agent_id>.jsonl` (recursive, components escaped; workflow agents sit in a subdirectory); at SubagentStop it uses `agent_transcript_path` and `last_assistant_message`, or, when that field is absent or empty, the text the agent wrote after its last tool use in the agent transcript. No match or field missing → no review evidence, K1 warn.
- Deny = exit 2, message on stderr. Warn = exit 0, stdout `{"hookSpecificOutput":{"hookEventName":"<event>","additionalContext":"<msg>"}}`. SubagentStop block = stdout `{"decision":"block","reason":"<msg>"}`. Input rewrite (model-assign) = `hookSpecificOutput.updatedInput`; the long-brief hint rides the same output as `additionalContext`, or is a plain warn when nothing is rewritten. In auto mode (`permission_mode` `"auto"`) model-assign denies instead of rewriting, naming the values to set, and the hint rides inside that deny. Its once-per-session stamp is `state/keel/sessions/<session>.brief-hint`, beside ship-gate's `registry-warned` stamp (nothing prunes either); a stamp that cannot be written means no hint.
- Message (`hookkit/protocol.ts`): line 1 `[<ID>] <hook>: <summary>` (`<ID>` = the first bullet's), then one `- [<ID>] …` line per finding; a deny ends with one last line (5.7), a warn does not; ≤ 2000 characters (a longer deny is cut before its last line, which survives).

Ported from v1 minus company branches: report-gate = evidence-token and `[SCOPE]` checks, hand-back/stop dedup, review evidence (5.6). git-guard = attribution regex, parser, fail-closed; secrets via `measure/boundary --staged --generic-only` on `git commit`; force push (`--force`, `-f`, `+refspec` denied; `--force-with-lease` only to the integration base, `main` or `master`); 5.6 protections; overlay repo rules. model-assign = v1 agent-model-assign without its `opus` ceiling: the hook knows only the names it acts on (`haiku` floor, `sonnet` default, `opus` for a judgment marker), and any other model a dispatch names or an agent file pins is kept as written, so a new tier needs no hook change. It does not check that a name exists; the Agent tool on Claude Code 2.1.326 was observed rejecting a name outside its own list before the hook ran, and nothing checks that the name in an agent file's `model:` pin exists. handoff = CLI modes only (its PreCompact `--auto` mode and registration were removed with C-handoff), snapshots in `$KEEL_DATA_DIR/handoff/`. env-preflight = repo→JDK map as overlay data.

### (j) Tests

- TypeScript: `tests/<track>/*.test.ts` and `codex/tests/*.test.ts`, `node --test`, names `<subject>_<expectedBehavior>_<condition>`, given/when/then, a failure-side test per branch; prefer black-box runs of the entry script or CLI as a subprocess. The `rule-checks` parity test compares the TypeScript with outputs recorded from the Python 3.15 implementation the TypeScript replaced (`tests/skills/fixtures`); the Python recordings of the other parity harnesses are deleted, and the tools that made them survive only in git history. The hook and ship-gate parity tests (`tests/hooks/fixtures`, `tests/ship-gate/fixtures`) replay the recorded runs against a golden snapshot of the node code's own output, re-recorded with `tests/hooks/hook-parity-record.ts` and `tests/ship-gate/ship-gate-parity-record.ts`. `measure`, `link` and `lib/evidence` keep only the outcomes of those recordings (exit code, JSON fields, stderr kinds, written files) in `tests/fixtures/measure`, `tests/fixtures/link` and `tests/fixtures/evidence`, and test the cases whose outcome changed with explicit expectations. The Codex adapter pins its input boundaries in a golden snapshot, `tests/fixtures/codex/boundary-recorded.json`, re-recorded with `codex/tests/boundary-record.ts`.
- Harness contract: `tests/hooks/fixtures/harness-contract/*.jsonl` are agent transcripts the harness really wrote (a reporter and a worker, each ending once in its final text and once in `SubagentHandback`), scrubbed by `tests/hooks/harness-contract-record.ts <transcript> <name>`: every string becomes `x` except the harness's own values under the keys `type`, `role`, `version`, `userType`, `entrypoint`, `renderedRole` and `stop_reason` and a tool block's `name` (an MCP server id rewritten to `mcp__server__`); inside a tool's `input`, `toolUseResult` and `wireToolInputs` every string becomes `x` whatever its key, `toolu_` keys are renumbered, and the fields report-gate consumes become `{{BRIEF}}`, `{{REPORT}}` and `{{EDIT_PATH}}`. Each fixture carries one harness `version`. `tests/hooks/harness-contract.test.ts` runs the real report-gate on them, with outcomes that come only from the transcript: the report read from the final text, a handback ending that is no contract miss, edits that need evidence, and an edit outside the brief's `[SCOPE]`. The hook payload around them stays synthetic (`tests/hooks/helpers.ts`), because no harness-written hook stdin is kept on disk; recording one envelope per event is an owner step. Re-record a fixture when the harness changes its transcript shape, and keep the old one while that version is still in use. A measure that reads a review report from a transcript takes it through `hooks/lib/hookkit/transcript.ts` `finalReport` (the final text after the last tool use, else the message of a closing `SubagentHandback`), which the same fixtures pin; `C-precheck`'s `mutation_tests_findings` read only assistant text before it and was null for every handed-back report.
- Node (review-engine): `tests/workflows/*.test.mjs`, `node --test`; workflow scripts run with stubbed `args`, `log`, `agent`, `workflow` globals.
- Per track: `node --test 'tests/<track>/*.test.ts'` (or `node --test 'tests/workflows/*.test.mjs'`). `bash tests/run-all.sh` runs `node --test` over `tests/**/*.test.ts` and `codex/tests/*.test.ts`, then the workflow tests; exit 1 if any failed. It exports `NODE_COMPILE_CACHE` as `$KEEL_DATA_DIR/state/keel/node-compile-cache` unless the caller set one, and `keel test --affected` does the same for its test run, so the many node processes a run spawns reuse compiled modules (one `keel home` spawn measured 151 ms without the cache and 121 ms with it). It first takes the machine-wide full-suite lock (`tests/suite-lock.sh`, a directory `$KEEL_DATA_DIR/state/keel/full-suite.lock` holding the runner's pid), since full runs started together time out under load: a second run waits and names the holder; a lock whose pid is gone, or that has had no pid for over a minute, is taken over under a second directory (`full-suite.lock.reclaim`) that re-reads the pid first, so a lock a new run took meanwhile stays; a takeover that cannot remove the lock, or a `.reclaim` left for over a minute, ends the run with 1 and names the path; only the holder removes it on exit, and TERM or INT ends the run with 143 or 130, stopping the suite it started. A suite still running after `KEEL_SUITE_TIMEOUT_SECONDS` (default 1800; a value that is not whole seconds without leading zeros ends the run with 2 before any suite starts) ends the run with 124: its processes' stacks go to `$KEEL_DATA_DIR/state/keel/suite-hangs/<time>-<pid>/` (`processes.txt`, one `sample` per pid, and the message counts the stacks saved), then the suite's process tree is frozen until a re-walk finds no new process, killed, and the lock released, so a hung test cannot hold the lock for the next run.
