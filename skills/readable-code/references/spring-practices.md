# Spring backend — writing reference

Written against the official reference documentation: Spring Framework 6.x, Spring Boot 3.x, Spring Data JPA, Hibernate ORM 6.x, MyBatis 3 (and mybatis-spring). Each bullet names the document and section it rests on, in parentheses, so a reviewer can check it against the source. No upstream rule-id set exists for Spring the way Vercel's does for React, so the section name is the citation. Stack-specific deltas (which rules a codebase already satisfies by config, local routing or pool facts, incident evidence) live in that project's own skill, not here.

Read before writing a service method that writes, a repository or mapper, anything `@Async`, `@Scheduled` or event-driven, an external call, a controller boundary, or a test. These are writing rules; a review blocks only on the items its own lenses name.

Three `/readable-code` rules already cover the Spring-specific ground and are not repeated: K5.9 (a new transaction boundary goes behind a named helper with a one-line why; a catch inside `@Transactional` states its rollback-only effect at the site), K5.11 (no entities past the controller; no `Map<String, Object>` hiding a shape), K5.12 (never swallow; log the exception object with identifiers; classify by type).

Sections run from the costliest class of defect to the cheapest.

## 1. Transactions (CRITICAL)

- **The service method is the transaction boundary, not the repository and not the controller** (Spring Data JPA › Transactionality: "the facade defines the boundary"; repository-level settings are neglected inside it). One use case, one `@Transactional` method; a controller never opens one.
- **Only a call that crosses the proxy is transactional** (Spring Framework › AOP › Understanding AOP Proxies, self-invocation; Transaction › Declarative › Using @Transactional, method visibility). A `this.method()` call ignores `@Transactional`, `@Async` and `@Cacheable`. A `private` method is never advised; with class-based proxies (the Boot default) `protected` and package-visible methods are advised as of Framework 6.0, with interface-based proxies only public ones. Move the method to another bean or call through the injected bean, never `AopContext.currentProxy()`.
- **Unchecked rolls back, checked commits, unless you say otherwise** (Transaction › Declarative › Rolling Back). Default rules: `RuntimeException` and `Error` roll back, checked exceptions do not. A checked exception that must roll back needs `rollbackFor`; a runtime exception that must not needs `noRollbackFor`. Do not invent a checked exception to "keep the commit".
- **A caught exception from an inner transactional call has already poisoned the shared transaction** (Transaction › Declarative › Rolling Back, rollback-only; `UnexpectedRollbackException` in Transaction › Understanding the Spring Framework Transaction Abstraction). With `REQUIRED` propagation the inner method marks the one physical transaction rollback-only before your catch runs; the outer commit then throws `UnexpectedRollbackException` and rolls back everything, after your "success" log. Either let the exception propagate, or isolate the inner work with `REQUIRES_NEW`, or make the inner read tolerant (return empty, do not throw) so there is nothing to mark.
- **`REQUIRES_NEW` means a second connection and a second commit** (Transaction › Declarative › Transaction Propagation). It cannot see the outer transaction's uncommitted rows, it holds a second pool connection for its duration, and its commit survives an outer rollback. Use it for audit rows and per-item isolation; never inside a loop over thousands of items.
- **Reads declare `readOnly = true`** (Transaction › Declarative › @Transactional Settings, `readOnly` "serves as a hint"; Spring Data JPA › Transactionality, flush mode set to `MANUAL`, "does not act as a check"). It lets Hibernate skip dirty checking, lets a routing datasource pick a replica, and documents intent. It is not a guard: a write inside a read-only transaction is silently not flushed with Hibernate, and a JDBC write may or may not be rejected by the driver. The flag states what the method does; the review checks that the body agrees.
- **Short transactions: no remote call, no file I/O, no user wait inside one** (Transaction › Declarative › @Transactional Settings, timeout). A transaction holds a connection and row locks for its whole duration. Call the external system before or after the boundary, and pass results in; an HTTP call inside `@Transactional` is a pool-exhaustion incident waiting for a slow peer.
- **Work that must happen only if the commit succeeds goes in `@TransactionalEventListener`** (Transaction › Transaction-bound Events; default phase `AFTER_COMMIT`). Sending a message, pushing to a queue or calling a webhook from inside the transaction publishes an uncommitted state and cannot be undone by the rollback.
- **No transaction is not the same as a write transaction** (Transaction › Declarative › Understanding the Spring Framework's Declarative Transaction Implementation). A mapper or template write outside any `@Transactional` runs in JDBC auto-commit on whatever datasource the routing picks for "no transaction"; a multi-statement write without a boundary is not atomic. Every write path has an explicit boundary, by annotation or `TransactionTemplate`.
- **Programmatic transactions use `TransactionTemplate`, not the manager API** (Transaction › Programmatic Transaction Management). Use it where the boundary is dynamic (per chunk, per item), and keep the callback free of checked exceptions.

## 2. Data access with JPA and Hibernate (HIGH)

- **Every `@ManyToOne` and `@OneToOne` is `fetch = LAZY`** (Hibernate ORM › Fetching › Fetching strategies; JPA default for to-one is EAGER). EAGER on a to-one loads the whole graph on every `find` and cannot be switched off per query; LAZY can be joined in when needed.
- **One query per screen, not one per row** (Hibernate ORM › Fetching › The N+1 problem; Spring Data JPA › JPA Repositories › Configuring Fetch- and LoadGraphs). A loop that touches a lazy association issues one select per iteration. Fetch the association in the query (`join fetch`, `@EntityGraph`), or batch it (`@BatchSize`, `hibernate.default_batch_fetch_size`), or load the set once into a `Map` keyed by id before the loop.
- **Lists are bounded** (Spring Data JPA › Defining Query Methods › Paging, Iterating Large Results, Sorting and Limiting; `Pageable`, `Slice`, `Limit`). A repository method that can return the table returns a page or a slice, or is called with an explicit limit. A `findAll()` on a growing table is a slow-query incident on a date you do not choose.
- **A page over a fetched collection is paginated in memory** (Hibernate ORM › Fetching › "firstResult/maxResults specified with collection fetch; applying in memory"). Paginate the parent ids first, then fetch the collection for those ids, two queries.
- **Read-only projections for read-only screens** (Spring Data JPA › Projections: interface and DTO projections, constructor expressions). Selecting the columns the screen uses avoids loading, dirty-checking and serializing fifty columns per row.
- **Bulk updates by statement, not by loading** (Spring Data JPA › Modifying Queries, `@Modifying`, `clearAutomatically`). A JPQL `update … where …` touches no entity; after it, the persistence context is stale, so clear it or do not read those rows in the same transaction.
- **Batch inserts need a non-`IDENTITY` generator and the batch properties** (Hibernate ORM › Batching › JDBC batching; `hibernate.jdbc.batch_size`, `hibernate.order_inserts`, `hibernate.order_updates`). With `IDENTITY` Hibernate must execute each insert to learn the id, so batching is disabled; use a sequence with an allocation size, or JDBC batch through the mapper.
- **`saveAll` inside one transaction, and flush and clear per chunk on large imports** (Hibernate ORM › Batching › Session-level batching; Spring Data JPA › `saveAll`). The persistence context holds every managed entity until commit; a 100k-row import without `flush()` and `clear()` per chunk grows memory linearly and dirty-checks the whole set at every flush.
- **No `LazyInitializationException` fixes by `open-in-view`** (Spring Boot › Data › JPA and Spring Data, `spring.jpa.open-in-view` warning; Hibernate ORM › Persistence Context). Open Session in View keeps the session and a connection open for the whole request so views can lazy-load; the fix is to fetch what the response needs inside the service and return a DTO.
- **Enums map by name, never by ordinal** (Hibernate ORM › Basic Types › Enums, `@Enumerated(EnumType.STRING)`; default is `ORDINAL`). An ordinal column breaks on the first reorder; a column that already stores a code uses an `AttributeConverter`.
- **`equals` and `hashCode` on a natural id or on the assigned id, never on the generated id before persist and never on all fields** (Hibernate ORM › Entities › Identifiers, natural ids; Entities › "Implementing equals() and hashCode()"). A generated id is null until flush, so a `Set` of new entities with id-based equality collapses; compare with `instanceof`, not `getClass()`, because a lazy proxy is a runtime subclass of the entity (Hibernate ORM Introduction › Entities, the equals example: "check type with instanceof, not getClass()").
- **Know when the flush happens** (Hibernate ORM › Flushing: `AUTO` flushes before a JPQL or HQL query that touches the affected tables and before a native query through the `EntityManager` API; `COMMIT` mode skips it, and Hibernate's `FlushMode.MANUAL` on the session or query skips it until an explicit `flush()`). A query that must see an entity write made earlier in the transaction depends on the flush mode; a `StatelessSession`, a JDBC template or a MyBatis mapper never sees unflushed entity state, so flush before mixing the two.
- **Optimistic locking for user-edited rows, pessimistic for counters and queues** (Spring Data JPA › Locking, `@Lock`; Hibernate ORM › Locking, `@Version`). A `@Version` column turns a lost update into an `ObjectOptimisticLockingFailureException` the user can retry; a `SELECT … FOR UPDATE` via `PESSIMISTIC_WRITE` serializes the few rows that must be.

## 3. Data access with MyBatis and JDBC (HIGH)

- **`#{}` binds a parameter; `${}` pastes a string** (MyBatis › Mapper XML Files › String Substitution; FAQ "Warning: ${} is vulnerable to SQL injection"). Every value from a request, a file or another table goes through `#{}`. `${}` is only for identifiers that come from a fixed allow-list in Java (a column name chosen from an enum), never from input, and never for a `LIKE` pattern (`<bind>` or build the wildcard in Java, then `#{}`).
- **Dynamic SQL uses `<where>`, `<set>`, `<trim>`, `<foreach>`, not string arithmetic** (MyBatis › Dynamic SQL). A hand-built `WHERE` with optional conditions produces `WHERE AND …` on the empty case; `<where>` strips the leading `AND`. A `<foreach>` over an empty collection emits nothing, so `IN <foreach open="(" close=")">` becomes a bare `IN` and `IN (<foreach>)` becomes `IN ()`, both invalid SQL; guard the empty list in Java.
- **`<foreach>` lists are chunked** (MyBatis › Dynamic SQL › foreach). Databases cap the number of bind parameters per statement and the optimizer gives up on very long `IN` lists; chunk ids at a fixed size (a few hundred to a thousand) and merge results.
- **Bulk writes use `ExecutorType.BATCH` or a multi-row `INSERT … VALUES`** (MyBatis › Java API › `SqlSession` and `ExecutorType.BATCH`, `flushStatements()`; mybatis-spring › `SqlSessionTemplate` with `ExecutorType.BATCH`). A mapper insert called in a loop on the default executor is one round trip per row.
- **Large result sets stream through `Cursor` or a `ResultHandler`, with a `fetchSize`** (MyBatis › Java API › `selectCursor`; Mapper XML › `fetchSize`). `selectList` materializes the whole result; an export or a sync reads row by row and never holds the table in memory.
- **Generated keys come back through `useGeneratedKeys` and `keyProperty`** (MyBatis › Mapper XML Files › insert). Not a second `SELECT LAST_INSERT_ID()`, which is wrong under batching and connection reuse.
- **A mapper write runs in the surrounding Spring transaction only when one exists** (mybatis-spring › Transactions: `SqlSessionTemplate` participates in the Spring-managed transaction; with none, each statement is auto-committed on a connection fetched from the `DataSource`). See §1 "No transaction is not the same as a write transaction".
- **A `resultMap` for anything with nesting or renamed columns** (MyBatis › Mapper XML Files › Result Maps). `resultType="map"` returns `Map<String, Object>` keyed by column name and hides the shape (K5.11); a typed result class, or a `resultMap`, keeps the contract visible.
- **Pool size is a shared budget, not a per-feature knob** (Spring Boot › Data › Configure a DataSource, `spring.datasource.hikari.*`). Every connection a feature holds for its whole duration (a long transaction, a streaming export, a `REQUIRES_NEW` inside a loop) is a connection no other request gets; size the hold, not the pool.

## 4. Asynchronous work, scheduling and events (HIGH)

- **`@Async` runs on the executor you configure, with the policy you configure** (Spring Framework › Task Execution and Scheduling › The `@Async` annotation, Executor qualification; Spring Boot › Task Execution and Scheduling, `spring.task.execution.*`). Name the executor on the annotation when more than one exists; an unbounded default queue turns a burst into an OOM, and a bounded one needs a rejection policy you chose (`CallerRunsPolicy` throttles, `AbortPolicy` fails fast).
- **An `@Async void` method's exception goes to `AsyncUncaughtExceptionHandler`, nowhere else** (Task Execution and Scheduling › Exception Management with `@Async`). Return a `CompletableFuture` when the caller must know, and complete it exceptionally rather than throwing (Transaction › Declarative › Rolling Back, "CompletableFuture with @Transactional @Async").
- **The transaction, the security context and the request do not follow an `@Async` call** (Task Execution and Scheduling › `@Async`; Transaction › Declarative, thread-bound resources). The async method starts its own transaction, if annotated, on another thread; pass ids, not managed entities, and re-load inside.
- **`@Scheduled` methods share one thread unless you size the scheduler** (Spring Boot › Task Execution and Scheduling, `spring.task.scheduling.pool.size` defaults to 1; Spring Framework › Task Execution and Scheduling › The `scheduler` Element, "If you do not provide a `pool-size` attribute, the default thread pool has only a single thread"). One slow job delays every other job; `fixedDelay` measures from the end of the previous run, `fixedRate` from the start, and overlapping `fixedRate` runs queue on the same thread.
- **A scheduled job on more than one node needs a lock or a leader** (Task Execution and Scheduling; the framework provides no cluster coordination). Two instances run the same cron twice; use a database lock row, ShedLock-style, or an external scheduler.
- **A listener that writes after commit opens its own transaction with `REQUIRES_NEW`** (`TransactionalEventListener` javadoc: in the `AFTER_COMMIT` and `AFTER_COMPLETION` phases "the transaction will have been committed or rolled back already, but the transactional resources might still be active", so "changes will not be committed to the transactional resource"; as of Framework 6.1 a listener annotated with plain `@Transactional` is rejected at startup unless it declares `REQUIRES_NEW` or `NOT_SUPPORTED`). A write in an unannotated after-commit listener is silently not committed.
- **One `AsyncConfigurer` per application context, and every `@Async` names its executor when more than one exists** (Task Execution and Scheduling › The `@Async` annotation, Executor qualification; `AbstractAsyncConfiguration` fails startup with "Only one AsyncConfigurer may exist"). A library module that ships its own `AsyncConfigurer` decides the executor policy for every application that scans it; a module exposes an executor bean with a qualifier, and leaves the configurer to the application.

## 5. External calls and failure modes (HIGH)

- **Every outbound call has a connect timeout and a read timeout** (timeouts live on the `ClientHttpRequestFactory`, not on `RestClient.Builder`: `SimpleClientHttpRequestFactory` has `setConnectTimeout` and `setReadTimeout`; `JdkClientHttpRequestFactory` has `setReadTimeout`, with the connect timeout set on the JDK `HttpClient.Builder` it wraps; `HttpComponentsClientHttpRequestFactory` takes them from the Apache client configuration; Spring Boot's `RestTemplateBuilder` sets both, `setConnectTimeout`/`setReadTimeout` before Boot 3.4 and `connectTimeout`/`readTimeout` after). The JDK `HttpURLConnection` default read timeout is 0, meaning infinite; a half-open peer then holds a request thread forever, and the thread pool drains one call at a time.
- **An external dependency gets its own bounded pool** (bulkhead; Spring Framework › Task Execution, `ThreadPoolTaskExecutor` sizing). When the printer or the payment gateway stalls, only its pool fills; the request threads for everything else keep serving.
- **A retry only on idempotent operations, with backoff and a cap** (Spring Retry is a separate project; Spring Framework 7 adds `@Retryable` in core). Retrying a non-idempotent write creates duplicates; every retry policy names the exceptions it retries and the ones it does not.
- **Partial failure is designed, not discovered** (Transaction › Declarative › Transaction Propagation). For a batch of N items decide in writing: all-or-nothing (one transaction, fail fast), per-item (a `TransactionTemplate` per item, collect failures, report counts), or chunked. "Catch per item and continue" inside one transaction is none of these; see §1 rollback-only.
- **Idempotency key for anything a client may resend** (HTTP semantics; no Spring primitive). A `POST` that creates money-bearing rows checks a client-supplied key or a natural unique constraint before inserting, and returns the earlier result on a repeat.
- **Validation of a batch happens before the first write** (Transaction › Declarative). Parse and validate the whole input, collect every error, then open the transaction; a transaction that fails on row 900 after writing 899 rows has done the expensive part for nothing.

## 6. Boundary: controllers, DTOs, validation, security (MEDIUM-HIGH)

- **A request DTO with Bean Validation at the controller, a response DTO out** (Spring Framework › Web MVC › Validation, `@Valid` on `@RequestBody`; Spring Boot › Validation). Validation annotations on the entity validate persistence, not requests; constraints that belong to the API (required fields, ranges, formats) live on the request type.
- **One exception handler, one error shape** (Spring Framework › Web MVC › Exceptions, `@ControllerAdvice`, `ProblemDetail` / RFC 9457). Each `@ExceptionHandler` maps an exception type to a status and a body with a correlation id; the body never includes a stack trace or an SQL message.
- **Constructor injection, `final` fields** (Spring Framework › Core › Dependency Injection › Constructor-based DI, "the Spring team generally advocates constructor injection"). Field injection hides required dependencies, allows a half-built object and needs reflection in tests.
- **`@ConfigurationProperties` with `@Validated` for every group of configurable values** (Spring Boot › Externalized Configuration › Type-safe Configuration Properties, `@ConfigurationProperties` Validation). A `@Value("${…}")` per use site spreads one key across the codebase, is untyped beyond the field, and cannot express a range or a required-together rule; an unresolved placeholder does fail the boot (Boot registers a `PropertySourcesPlaceholderConfigurer`), but a wrong value does not.
- **Security is declared on the request path and enforced at the method** (Spring Security › Authorization › Authorize HttpServletRequests; Method Security `@PreAuthorize`). A `permitAll` list in configuration is the real exposure surface; review that list, and the controllers under those paths, not the config class.
- **Jackson never serializes an entity** (K5.11; Spring Boot › JSON › Jackson). An entity with lazy associations and back-references either lazy-loads during serialization, recurses, or throws after the transaction closed; a response DTO decides the shape once.
- **Money is `BigDecimal` with a declared scale; time is `Instant` or `OffsetDateTime` with a declared zone** (Hibernate ORM › Basic Types; JDBC). `double` for a price and `LocalDateTime` across zones are silent data defects.

## 7. Configuration, beans and startup (MEDIUM)

- **A bean has one definition; a second definition is a review finding, not an override** (Spring Boot › Core Features, `spring.main.allow-bean-definition-overriding` defaults to `false`, so two definitions with the same bean name fail the boot with `BeanDefinitionOverrideException`). Two beans of the same type under different names fail at the injection point with `NoUniqueBeanDefinitionException` unless one is `@Primary` or the injection names a qualifier. Turning overriding on converts both startup failures into a silent last-one-wins.
- **Auto-configuration is replaced by declaring the bean, not by excluding and re-adding** (Spring Boot › Auto-configuration, `@ConditionalOnMissingBean` semantics). Declare the `DataSource`, `ObjectMapper` or `TaskExecutor` you want and the auto-configuration backs off.
- **Profiles select configuration, never behavior** (Spring Boot › Profiles). `if (env.acceptsProfiles("prod"))` in business code is a latent prod-only bug; put the difference in a property and bind it.
- **Startup validates what runtime would otherwise discover** (Spring Boot › `ApplicationRunner`, `@PostConstruct`; `@ConfigurationProperties` `@Validated`). A missing property, an unreachable required dependency or a mis-sized pool fails the boot, not the first request.
- **The request or job id rides in MDC, not in every log call** (Spring Boot › Logging, MDC in the log pattern; K5.12 covers what each line carries). A filter or a job wrapper puts the correlation id into MDC once and clears it in `finally`; an `@Async` or scheduled thread does not inherit it, so the task decorator copies it.

## 8. Tests (MEDIUM)

- **A slice for the layer under test, the full context only for wiring tests** (Spring Boot › Testing › Auto-configured Tests: `@WebMvcTest`, `@DataJpaTest`, `@JdbcTest`; `@MybatisTest` from `mybatis-spring-boot-starter-test`). `@SpringBootTest` boots everything and shares a cached context across classes; one per test class hides startup cost and couples tests to unrelated beans.
- **`@DataJpaTest` is transactional and rolls back; a test of flush-time behavior flushes** (Spring Boot › Testing › Auto-configured Data JPA Tests; `TestEntityManager.persistAndFlush`). An assertion that passes against the persistence context but fails against the database (constraint violations, `@Version`, generated columns) needs the flush.
- **The database in a persistence test is the real engine** (Spring Boot › Testing › Testcontainers, `@ServiceConnection`; `@AutoConfigureTestDatabase(replace = NONE)`). H2 accepts SQL the production engine rejects and rejects SQL it accepts; dialect-specific statements, locks and `ON DUPLICATE KEY` are untested on H2.
- **A transaction-boundary bug is tested without a test transaction** (Spring Framework › Testing › Transaction Management; `@Transactional` on a test wraps the whole test in one rollback-only transaction). Propagation, `REQUIRES_NEW`, rollback-only and `AFTER_COMMIT` listeners behave differently inside the test's transaction; test them with `TransactionTemplate` or `@Commit`, against the real boundary.
- **Mocked dependencies are the boundary, not the layer below** (Spring Boot › Testing › Mocking and Spying Beans: `@MockitoBean` on Framework 6.2 / Boot 3.4 and later, `@MockBean` before). A service test that mocks the repository tests the service; a controller test that mocks the service tests the controller; a test that mocks both tests the mocks.
